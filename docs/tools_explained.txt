TOOLS.PY — THE AGENT'S LOCAL ACTIONS
====================================

Purpose
-------
tools.py contains the actions the Llama agent is allowed to request. They are
ordinary Python functions, but Ollama can see their names, type hints, and
docstrings and use that information to decide which one to call.

The first version uses only local, deterministic tools. This keeps the project
safe and reproducible while we learn how telemetry works.


1. FILE LOCATIONS
-----------------
PROJECT_ROOT is the project folder. DATA_DIR is the project's data folder.
The two data sources are:

- data/knowledge_base.txt: a small local text document.
- data/demo.sqlite3: a small file-based SQLite database.

SQLite comes with Python. It is not a separate database server. The .sqlite3
file is the database itself.


2. initialise_demo_data()
-------------------------
This function creates the demo sources if they do not exist yet.

For the text document, it writes a few lines of sample knowledge.

For SQLite, it:

1. connects to data/demo.sqlite3;
2. creates a customers table if it is missing;
3. checks whether the table is empty;
4. adds three sample customer rows only when needed.

The "if it does not exist" behaviour is important. It means rerunning the
agent will not continually recreate the database or duplicate sample rows.


3. calculate(expression)
-------------------------
This tool evaluates basic arithmetic, for example:

    calculate("25 * 17")
    returns "425"

It does NOT use Python's eval(), because eval() could execute arbitrary Python
code. Instead it parses the expression into an abstract syntax tree (AST) and
allows only numbers and a small, explicit set of operators:

- +, -, *, /, //, %, **
- unary + and -

Anything else raises ValueError. That makes the calculator safer and makes
failures visible to telemetry.


4. search_documents(query)
--------------------------
This tool searches data/knowledge_base.txt.

It turns the query into words, then returns document lines that share at least
one word with the query. If nothing matches, it returns:

    "No matching documents found."

This is intentionally a very basic document search. Later, we could replace
it with keyword ranking, embeddings, or a vector database. The current simple
version is useful because its behaviour is predictable.


5. query_database(sql)
----------------------
This tool runs a read-only query on data/demo.sqlite3.

It permits only one SQL SELECT statement. It rejects statements that do not
start with SELECT and rejects semicolons. This prevents Llama from modifying
or deleting the database.

Example:

    SELECT name FROM customers WHERE balance > 1000

The tool fetches up to 25 rows and returns them as a string of dictionaries.

The real project can later add realistic database failures: unavailable
database, slow query, invalid SQL, empty results, or permission errors.


6. AVAILABLE_TOOLS
------------------
AVAILABLE_TOOLS is a dictionary that connects a tool name to its function:

    "calculate"        -> calculate
    "search_documents"  -> search_documents
    "query_database"    -> query_database

runner.py gives the functions to Ollama and uses this dictionary to safely
find the requested function. A requested name that does not exist causes an
error instead of running anything unknown.


7. HOW A TOOL CALL FLOWS
------------------------
Llama says: "Call calculate with expression = 25 * 17."

runner.py finds calculate in AVAILABLE_TOOLS.

tools.py executes calculate("25 * 17") and returns "425".

runner.py logs the latency and success/failure, then gives "425" back to
Llama so it can answer the user.
